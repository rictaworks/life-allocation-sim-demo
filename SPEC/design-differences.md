# 設計書との差

設計書（`requirements.md`）と実装の違いを書きます。違いの判断は、CLAUDE.md の規定（設計書との差は確認事項とする）に従います。

「状態」は次の意味です。

- 実装済み：設計書と違うが、判断は済んでいて、コードとテストで確かめています。
- 確認事項：判断が必要です。PR 本文の「確認事項」に載せています。
- 未解決：設計書の要件を満たしていません。判断を待っています。

## 1. seed の扱い（DFD と 9 章）

- 設計書：DFD と 9 章のシーケンスは、配分の履歴とシードを保存要求で送るように描いています。
- 実装：seed は、新規ゲームの開始時にサーバーが生成して保存します（0 以上 2^63−1 の整数）。保存要求では受け取りません。保存要求が送るのは、今年の配分（`turn_no`・`living_pct`・`saving_pct`・`invest_pct`）と `website` だけです。履歴は DB から読みます。
- 理由：クライアントから送られた値を信用しないため（設計書 5 章「クライアント送信の状態値は信用しない」）。seed を変えられると、結果を選べてしまうため。
- 状態：実装済み。図との差として確認事項に載せています。

## 2. ハニーポット（設計書 2 章と 9 章）

- 設計書：不可視の入力欄に値が入った保存要求を破棄するとしています。
- 実装：Unity の描画には入力欄が無いため、保存 JSON の `website` を使います。`website` が空文字列・`null`・省略のときは、通常どおり保存します。空でない値が入っていれば、通常と同じ 201 の応答（TURN と GAME）を返しますが、保存しません。
- 理由：CLAUDE.md の規定どおり、ハニーポットは補助策です。主な防御は、大きさの上限（8KB）と頻度の上限です。
- 状態：確認事項。

## 3. 保存の内容（DFD）

- 設計書：配分履歴・シードを送るとしています。
- 実装：1 年ぶんの配分だけを送ります（1 の seed と同じ理由）。応答の数値は、すべてサーバーの再計算の結果です。
- 状態：実装済み。

## 4. セッションと保存先（ER 図）

- 設計書：SESSIONS の主キーは `session_id`。
- 実装：`sessions` の主キーは整数の `id`。Cookie の値は 32 バイトの乱数で、DB には SHA-256 のハッシュ（`token_digest`）だけを保存します。`games`・`turns` は `session_id` を持ち、検索は必ずセッションで絞り込みます。`request_events` は頻度の数え上げにだけ使い、ダイジェストだけを保存します（設計書の ER 図には無い表）。
- 理由：CLAUDE.md（DB にはハッシュを保存する）。Cookie の値が漏れても、DB の値から Cookie を作れないようにするため。
- 状態：実装済み。

## 5. 毎日 JST 03:00 の全データ削除（設計書 2.1）

- 設計書：Railway の cron ジョブで、JST 03:00 に全データを自動削除するとしています。
- 実装：全データを削除するコマンド（`bin/rails lasd:reset_all`）は実装済みです。`sessions`・`games`・`turns`・`request_events` の全行を、1 つの transaction で削除します。件数だけを標準出力に出します。何度実行しても失敗しません。アプリの画面の読み込みで削除することはありません。
  - Railway の cron サービスへの設定は、デプロイ時に設定する手順です（未確認。ボリュームの共有は実機で確認する）。スケジュールは `0 18 * * *`（cron は UTC で解釈するため、UTC 18:00 = JST 03:00）です。
- 未確認：cron サービスと Web サービスで、SQLite のボリュームを共有できるかは実機で確認します。共有できない場合は、この方式（同じボリュームを読む cron）を変える必要があります。
- 状態：確認事項。

## 6. リセット後の再開（設計書 5 章）

- 設計書：03:00 のリセットをまたいでプレイ中だった場合は、次回保存時に「データがリセットされた」旨を表示し、新規ゲームを開始させるとしています。
- 実装：リセットでセッションも消えるため、Cookie は無効になります。
  - 次の年への保存（`POST /api/games/turns`）は 401（`session_required`）になります。ゲームの途中でこの 401 を受けた画面は、「データがリセットされました。新しく始めてください。」を表示して、タイトルへ戻ります（Unity の `HandleFailure`）。
  - ゲームの途中以外で受けた 401 は、「セッションを確認できませんでした。ページを再読み込みしてください。」を表示します。
  - 再読み込みすると、新しいセッションが作られ、`GET /api/game` は `game` が `null` になります。画面はタイトルに戻ります。
  - 404（`game_not_found`）も、同じ「データがリセットされました。新しく始めてください。」を表示します。
- 状態：実装済み（画面の文言は、設計書の「データがリセットされた」旨の表示に当たります）。ブラウザで 401 の画面を確かめるのは未確認です（PR 本文の未確認の範囲）。承認は確認事項です（PR 本文の確認事項 12）。

## 7. 生活困窮の表し方（設計書 3.3）

- 設計書：状態は「プレイ中／生活困窮／破綻／完走」の 4 つです。
- 実装：`games.status` と API の `status` は `playing`・`completed`・`bankrupt` の 3 つです。生活困窮は、`status` が `playing` のまま、`state.struggling` が `true` で表します（再計算ホストの出力。`Protocol.md`）。
- 理由：再計算ホストの出力の形を、そのまま使うため。
- 状態：実装済み。

## 8. 配分の検査の場所（設計書 4.1）

- 設計書：`validateAllocation` が 0〜100・5 刻み・合計 100 を検査するとしています。
- 実装：規則の検査は Domain Core だけが行います（再計算ホストが呼び出します）。Rails は、キーの有無と JSON の整数の型だけを検査し、配分の範囲・刻み・合計は見ません。整数の大きさにも上限を置きません。32 ビットの範囲の外の値も、ホストが規則の理由コードで 422 にします（`allocation_negative`・`allocation_step_mismatch`・`allocation_sum_mismatch`）。
- 理由：規則を Rails に複製しないため。32 ビットに限ると、範囲の外の値が 400 になり、規則の理由コードが返らないため。
- 状態：実装済み。設計書の検査の場所（Domain Core）とは、Rails が呼び出す点だけが違います。

## 9. 完走・破綻のあとの再送（設計書 4.3 と 5 章）

- 設計書：完走・破綻したら最終評価へ進むとしています。完走・破綻のあとの保存は定めていません。
- 実装：ゲームが完走・破綻したあとは、新しい番号の保存も、保存済みの番号の再送も、409（`game_finished`）です。ホストは呼びません。最終結果は `GET /api/game` で読みます（評価を含む GAME を返します）。
- 理由：ゲームが終了していれば 409（保存済みの番号の再送でも同じ）とする Issue #8 の受け入れ条件 4 に合わせるため。
- 状態：実装済み。CLAUDE.md の「同じ番号の再送は同じ結果を返す」とは、完走・破綻のあとで食い違います。この点は確認事項です（PR 本文に載せます）。

## 10. 頻度の制限（設計書 5 章）

- 設計書：保存 API は、リクエストサイズ上限とセッション単位の頻度制限を持つとしています。数値は定めていません。
- 実装：CLAUDE.md の数値を使います。
  - 保存（新規と再送を同じ枠で数える）：セッションごとに 1 秒 1 件・1 分 20 件。
  - ゲームの開始：保存と同じ数値（設計書には無い制限）。
  - 新規セッション：接続元 IP ごとに 1 分 10 件。
  - 本体：8KB まで。
  - `GET /api/game`：頻度を数えません。状態を変えない読み取りのため、CLAUDE.md の「状態を変えるのは POST だけ」に従い、記録（request_events）も残しません。ゲームがあるときは毎回、再計算ホストを呼びます。その負荷は、ホストの同時実行の上限（2 件）と制限時間（5 秒）で守ります。設計書には無い扱いです。
- 状態：ゲームの開始の制限と、`GET /api/game` を数えない扱いは確認事項。`GET /api/game` に頻度の上限を残す場合の代わりの守り方は、次のどちらかです。（a）今の扱いのまま、ホストの上限で守る。（b）ゲームの状態を保存時に確定させ、読み取りでホストを呼ばない（保存の仕組みの変更）。

## 11. 画面の照合（設計書に無い確認）

- 設計書：サーバーは保存時に再計算し、画面はその結果を表示するとしています。
- 実装：Unity は、保存の応答（TURN）の残高と、自分の Domain Core の計算結果を照合します。一致したときだけ次の年へ進み、一致しなければ「保存された結果を確認できませんでした。最新の状態を読み込んでください。」を表示します。
- 状態：実装済み。

- CLAUDE.md：UI の実装 Issue の前に、組織のデザインシステムから選ぶとしています。今回は選定していません。
- 状態：確認事項。
